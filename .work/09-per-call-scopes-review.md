# Independent review: per-call scopes

Review basis: `.work/09-per-call-scopes.md`, the implementation diff against `d61505b`, and independent focused probes on `codex/per-call-scopes`. Final disposition: no outstanding required fixes after the repair cycle.

## Findings resolved during review

1. **P1 — Synchronous contract can return a coroutine after scope cleanup** (`clean_ioc/container.py`, `_validate_per_call_implementation`, initially lines 2426–2445; `_per_call_proxy_type`, initially lines 2395–2409). A Protocol declares `def run(self): ...`; its implementation declares `async def run(self): return "ok"`. Registration with `scope="per_call"` builds. `handle.run()` returns a coroutine, which is not awaited, and its invocation scope has already exited. Reject statically detectable coroutine-mode mismatch between declared operation and implementation/decorators at build time.

2. **P1 — Detectable streams escape a closed operation scope** (`clean_ioc/container.py`, `_per_call_methods`, initially lines 2306–2365; `_validate_per_call_implementation`, initially lines 2426–2445). A contract declares `def stream(self) -> Iterator[Resource]`; an implementation returns `iter((self.resource,))` without using a generator function. Build succeeds. The returned iterator yields a resource with `closed is True` because scope cleanup preceded iteration. Separately, an explicit decorator with `def run(self): yield self.child.run()` builds and its body runs only after scope exit. Reject declared iterator/async-iterator operations and known generator operations anywhere in the decorated target pipeline. A factory annotated with a string result type can also hide a generator implementation from the current `normalize_implementation_type` inspection.

3. **P2 — Unsupported descriptors produce partially usable handles** (`clean_ioc/container.py`, `_per_call_methods`, initially lines 2306–2365; `_validate_per_call_implementation`, initially lines 2426–2445). A contract with `@cached_property def state(self): return self._resource` and a public method builds; reading `handle.state` runs the descriptor on the proxy and raises `AttributeError` because the target's `_resource` exists only inside each invocation. A Protocol method implemented as `@property` likewise builds, then `handle.run()` raises `TypeError: 'str' object is not callable`. Reject public descriptors on the contract and non-callable operation implementations with actionable build errors.

4. **P2 — Invocation scope provisions remain mutable after activation begins** (`clean_ioc/container.py`, `_per_call_proxy_type`, initially lines 2378–2410). The forwarding path resolves `target_step` directly and does not mark its fresh `Scope` as having begun resolution. Given a declared `Request` slot and a target that receives `Scope`, its `run` method can call `scope.provide(Request, ...)` after the graph has activated, whereas public `Scope.resolve` locks provisions first. The parent independently reproduced this. Lock the invocation scope before target activation in both sync and async forwarding paths, while preserving reads of inherited provisions.

5. **P2 — Repair's annotation scanner rejects safe results and can raise `TypeError`** (`clean_ioc/container.py`, `_per_call_stream_annotation`, introduced during repair). Contract `def run(self) -> Literal["Iterator"]` returning scalar `"Iterator"` is rejected as a stream. `Annotated[str, "Iterator"]` is also rejected. A matching method annotated `-> Callable[[int], int]` causes a generic `compile-error` because recursion reaches Callable's unhashable parameter list and tries set membership. The scanner must inspect actual return type structure, not literal values or metadata, and handle all `get_args` shapes. Separately, an `Iterable[int]` annotation with an eager `[1, 2]` result is rejected, even though it is an ordinary materialized result. Narrow static rejection to actual iterator/generator declarations, with runtime checks for unknown actual iterators.

6. **P2 — Known Protocol backport is rejected on Python 3.11** (`clean_ioc/container.py`, `_per_call_methods` metaclass check). The parent reproduced that a method-only `typing_extensions.Protocol` registration with `scope="per_call"` fails as a custom metaclass on Python 3.11, while the same contract succeeds on 3.14. Recognize the standard backport metaclass while continuing to reject arbitrary custom metaclasses.

All six findings above were sent to the implementer and repaired. The final independent probes confirmed build-time rejection of known async-mode mismatches, descriptors, declared iterators, generator decorators, and invalid operation implementations. Unknown-factory awaitable/iterator results fail during invocation before scope exit. Dynamic implementation and decorator method delegation still work. Invocation provisions lock before target construction. Safe scalar `Literal["Iterator"]`, `Annotated[str, "Iterator"]`, eager `Iterable[int]`, and `Callable[[int], int]` results pass unchanged. A method-only `typing_extensions.Protocol` works on Python 3.11.

## Follow-up: private abstract ABC helpers

The user-approved follow-up adds raising stubs for unresolved private abstract ABC members on the generated handle. Inherited and name-mangled abstract helpers, an abstract initializer, private async helpers, and private property/static/class helpers are covered by the new tests. Before the two review repairs below, the parent reported `make ci` passing with **788 tests** and the implementer reported **45 focused tests passing on Python 3.11–3.14**, plus passing Ruff, type checks, and strict documentation build.

The independent follow-up review found two P2 defects in the first stub revision (`clean_ioc/container.py`, `_per_call_proxy_type` around lines 2540–2556):

- The `name.startswith("_")` private check also accepts public special methods such as abstract `__str__`. A service with abstract `__str__` and public `run` now builds, but `str(handle)` raises the private-helper stub error. These special methods should not silently become private helper stubs; reject unsupported public operations (or explicitly forward those supported).
- An abstract private property with a concrete getter and abstract setter is replaced by a getter-only property. Direct `handle._state = "x"` raises an incidental `AttributeError` about a missing setter, while direct read raises the intended `NotImplementedError`. Preserve and stub each declared property mode, or reject unsupported shapes clearly at build. The same concern applies to deleters.

Both defects were reproduced independently and sent to the parent. The repaired version rejects unsupported abstract special methods while preserving generated `__init__` and forwarded `__call__`, and keeps getter, setter, and deleter modes as raising stubs. Independent probes confirmed public dispatch still works; direct private getter/setter/deleter access raises `NotImplementedError`, and abstract `__str__` fails at build with `per-call-unsupported-member`. The repaired focused feature and acceptance suite passed locally: **47 passed**. No outstanding required fix remains in this follow-up. The parent reports final `make ci` passing with **790 tests**; the implementer reports **47 focused tests passing on Python 3.11–3.14**, with lint, type checks, and strict documentation build passing.

## Follow-up: class shape and scoped-result hardening

The user authorized another hardening pass for inherited hooks, effective annotations, fluent return declarations, and scoped target escapes. The parent's acceptance tests cover hook rejection without activation, safe object representation and identity behavior for handles, and sync/async target or bound-method returns through decorators. The implementation is under independent review; validation is provisional until the repair cycle finishes.

Confirmed findings sent to the parent for repair:

- `_checked_per_call_result` checked Python methods and builtins but missed bound `method-wrapper` values such as `self.__str__`. A per-call `export() -> object` returning that wrapper escaped after invocation scope exit; `inspect.ismethodwrapper(result)` and `result.__self__ is target` were both true.
- `_per_call_methods` applied an inherited `ClassVar` annotation even when a derived service class replaced that member with a public method. The generated handle skipped forwarding it; direct `handle.data()` executed the inherited method against the handle and failed on target-only state, while another public method forwarded and worked.
- Unsupported special-member detection inspected only functions and a few built-in descriptor categories. A custom callable object assigned to `__getattribute__` passed build, then `handle.run()` failed through that inherited hook. Unknown unsupported dunder hook shapes need actionable build diagnostics.
- A private abstract contract member named `_per_call_scope` collided with the generated handle's slot and produced a generic `compile-error`; nonabstract members with either reserved slot name risk being shadowed by runtime owner/target fields. Explicit reserved-name validation is needed.
- The first repaired ClassVar parser still rejects valid bare `status: ClassVar` and explicitly quoted `status: 'ClassVar[str]'` under postponed annotations, classifying them as public instance data. The latter's runtime annotation string includes outer quote characters. Recognize these declarations without evaluating arbitrary annotation text.

All five findings were repaired and independently rechecked. The final local feature and acceptance suite passed **78 tests**. Independent probes confirmed method-wrapper escape rejection, forwarding of a subclass method over an inherited ClassVar, named build errors for custom callable hooks and reserved names, unchanged returns for independent values whose equality raises, acceptance of bare and postponed quoted ClassVar, and build rejection of postponed quoted Self. The implementer reports the **78 focused tests passing on Python 3.11–3.14**, with targeted lint, formatting, and type checks passing. The per-call instance capture now uses a dedicated target step and resolution context; the parent confirmed the ordinary activation/context code remains unchanged from baseline. The parent reports final `make ci` passing with **821 tests**, a passing strict MkDocs build, and a clean diff check. No outstanding required issue remains in this hardening review. No production or existing-test files were edited by the reviewer.
